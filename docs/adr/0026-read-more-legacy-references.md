# ADR 0026: 旧形式のステータス行の修正先を、リンク先と裸の番号からも読む

Status: accepted-pending

## 文脈

[ADR 0022](0022-status-transitions.md) は、旧形式のステータス行を新形式に書きかえるとき、旧形式の修正先を移行前のツリーで解決し、新形式の修正先と比べると定めた。
修正先の解決は、[ADR 0023](0023-trace-amendments.md) の規則による。
この規則は、`ADR NNNN` の形の参照と、`→` の直後に区切って並べた裸の番号だけを、修正先として読む。
裸の番号は、文書のディレクトリと祖先のADRのディレクトリから、番号の一致するADRを探して修正先とする（`src/links.rs` の `candidate_dirs` の順）。

そのため、修正先がリンク先として行の中に書かれていても、その参照が上の形でなければ、旧形式の行は解決できない。
解決できない行は、移行スクリプト（`scripts/migrate-adr-status`）で移せない。
人や AI が新形式の行を手で書いても、pre-commit と `check-range` が `修正先の番号がありません` で止める。

この ADR は、旧形式の参照の読み方を広げ、行の中に書かれた修正先を読めるようにする。
検査そのもの（旧形式の修正先と新形式の修正先を比べること）は緩めない。

## 調査した事項

[ADR 0024](0024-migration-dry-run-and-error-count.md) の `--dry-run` を、tett23 のリポジトリ（dotfiles を含む）で実行した。
移行できないADRのうち、次の40件は、修正先がすべて行の中に書かれているのに、移行スクリプトで移せない。
40件の行の全文を読み、行の中のリンクのリンク先がすべて実在のADRを指すことを確かめた。

| 形 | 件数 | 例 |
|---|---|---|
| リンクの文字が `ADR NNNN` の形でない | golem 28 | ``記法と `stanza-gap` は [docs/adr/0005](0005-character-and-paragraph-styles.md)``、`コードの形は [docs/adr 0061](../../adr/0061-five-digit-diagnostic-codes.md)` |
| 最後の参照の後ろに注記がある | golem 7、dotfiles 1 | `` `toolsRequiredBy` は [ADR 0092](0092-remove-tools-required-exports.md) で消した ``、`Ctrl-T のプレビューは[ADR 0036](…) (Ctrl-P だけになる)` |
| 最後の参照の後ろが閉じ括弧だけ | golem 1 | ``…は [ADR 0010](…)（`golem check` が…は [golem-project ADR 0004](…)）`` |
| 英語の `Accepted` に `→` と裸の番号が続く | dotfiles 3 | `Status: Accepted → 0031` |

最後の参照の後ろに注記があるとき、いまの `src/status.rs` の `changes_ja` は、その注記を修正先のない変更として加える。
`src/revisions.rs` の `resolve_legacy` は、修正先のない変更があると `修正先の番号がありません` を返す。

一時リポジトリで、この3つの形の旧形式の行をコミットしてから、手で新形式に書きかえて `pre-commit --allow-status` を実行した。
リンクの文字が番号でない行と、後ろに注記がある行は、どちらも `修正先の番号がありません` で止まった。
`採択、y の除き方は [ADR 0002](0002-b.md)` の形（読点の形）は、旧形式では「採択」と読まれるので、通った。

ほかに、send-to-kindle の4件（`採択→[0004](0004-continuous-integration.md)、[0009](…)`）は、`修正先の参照を対応づけられません` で止まる。
変更への分け方の段階（`src/status.rs` の `changes_ja`）は、リンクの文字を取り出した `0004、0009` を裸の番号として読める。
しかし、参照を数える段階（`src/revisions.rs` の `references`）は、リンクの記法を残した元の行を `→` の後ろで区切るので、`[0004](…)` を4桁の数字として読めない。
そのため、変更の修正先の数と参照の数が合わない。

いまの規則で解決できる行の、変更への分け方も確かめた。
一時リポジトリで `trace` を実行した結果は次のとおりである。

| 旧形式の行（`ステータス: ` の後ろ） | いまの変更の列 |
|---|---|
| `採択→a は ADR 0002、ADR 0003`（リンクの有無によらない） | 部分名 a の変更（修正先 0002）と、部分名なしの変更（修正先 0003）の2件 |
| `採択→a は ADR 0002、0003` | 部分名 a の変更1件（修正先 0002 と 0003） |
| `採択→a は ADR 0002 と ADR 0003` | 部分名 a の変更（修正先 0002）と、部分名「と」の変更（修正先 0003）の2件 |
| `採択→0004、0009` | 部分名なしの変更1件（修正先2件） |

いまの `parse` は、`Accepted → 0031` を Accepted と読む（`src/status.rs` の `parse` は、`english(raw, "accepted")` を `Superseded` の判定より先に評価する）。
そのため、この形の行を手で新形式の superseded に書きかえるコミットは、Accepted から Superseded への遷移（Revise）として検査を通る。
一時リポジトリで、`Status: Accepted → 0031` をコミットしてから `Status: superseded [{"part":null,"by":["docs/adr/0031-x.md"]}]` に書きかえると、`pre-commit --allow-status` と `check-range --allow-status` はどちらも終了コード0で終わった。
この形の3件（dotfiles）は、この ADR の対象にしない。
人か AI が新形式で書く。

## 用語

この ADR では次の語を使う。

- 参照：旧形式のステータス行の中で、修正先を一つ指すもの。
- リンクの参照：Markdown のインラインのリンクで、リンク先がリポジトリの中の相対パスであるもの。
- 区切り：二つの参照のあいだにあり、二つめの参照が一つめと同じ変更に属することを示す文字列。
- 変更：[ADR 0022](0022-status-transitions.md) の変更。部分名と修正先の列を持つ。
- 部分名：変更が対象とする、元のADRの部分の名前（[ADR 0022](0022-status-transitions.md) の `part`）。
- 注記：変更に付ける自由な文（[ADR 0025](0025-extend-canonical-status-amendments.md) の `note`）。

## 実装すること

### 参照の読み方

旧形式の参照を、次の3つとする。
1つめと3つめは [ADR 0023](0023-trace-amendments.md) のままで、2つめをこの ADR で加える。

1. `ADR NNNN` の形の参照（リンクの中と外の両方）。
2. リンクの参照のうち、リンクの文字に `ADR NNNN` の形を含まないもの。リンク先のファイル名の先頭の4桁の数字を、参照の番号とする。リンクの文字の中に、前後が数字でない4桁の数字の並び（`docs/adr/0005` の `0005`）があれば、そのすべてがリンク先の番号と等しくなければならない。等しくなければ、`ADR <番号> のリンク先 <パス> の番号が違います` のエラーとする。
3. `→` の直後に区切って並べた裸の番号（`採択→0004、0005`）。

2つめの参照の修正先は、[ADR 0023](0023-trace-amendments.md) と同じく、リンク先を文書のディレクトリから解決したパスとする。
リンク先は作業ツリーのADRの一覧になければならない。
リンク先が `https://` で始まる URL のものは、[ADR 0025](0025-extend-canonical-status-amendments.md) のとおり URL の修正先とする。

### 変更への分け方

参照を、行の中の順に変更へ分ける。
変更の部分名は、いまと同じく、前の変更の後から参照の前までの文字列から、前後の空白、先頭の読点、末尾の `は` を除いたものとする。

二つの参照のあいだが区切りだけなら、二つめの参照は一つめと同じ変更の修正先に加える。
区切りは、空白を除いて、`、`、`,`、`と`、`および` のいずれかとする。
この規則は、3つの形のどの参照にも当てる。

- `索引の段組みは [docs/adr/0018](…) と [docs/adr/0025](…)` は、部分名「索引の段組み」の変更1件で、修正先2件となる。

この規則により、いまの規則で解決できる行のうち、参照のあいだに区切りだけをはさむ行の変更の列が変わる。

- `採択→a は ADR 0002、ADR 0003` は、2件の変更（2件めは部分名なし）から、部分名 a の変更1件（修正先2件）になる。
- `採択→a は ADR 0002 と ADR 0003` は、2件の変更（2件めの部分名は「と」）から、部分名 a の変更1件（修正先2件）になる。

変わるのは、旧形式の行の読み方だけである。
新形式に移した行は変わらない。
旧形式と新形式の比較は、旧形式の行を新形式に書きかえるコミットでだけ行う（[ADR 0022](0022-status-transitions.md)）。
そのため、すでに新形式に移した行の検査には影響しない。

### 最後の参照の後ろ

最後の参照の後ろの文字列は、修正先を持たない変更として加えない。
旧形式の行から得た変更の列は、修正先のある変更だけからなる。

最後の参照の後ろの文字列は、前後の空白と読点を除いて、次のとおり扱う。

- 空、または閉じ括弧（`）`、`)`）だけなら、捨てる。
- 前後の括弧を除いて、`は` で終わる文字列なら、修正先の抜けとして、いまと同じく `修正先の番号がありません` のエラーとする。
- それ以外は、注記とする。

注記は、旧形式と新形式の比較（pre-commit、`check-range`）には使わない。
[ADR 0025](0025-extend-canonical-status-amendments.md) のとおり、旧形式の行から得た変更は注記を持たない。

### 移行スクリプト

移行スクリプトは、最後の参照の後ろの注記を、最後の変更の `note`（[ADR 0025](0025-extend-canonical-status-amendments.md)）に入れて移す。
注記の前後の括弧は除く。

- `` 採択→`toolsRequiredBy` は [ADR 0092](0092-remove-tools-required-exports.md) で消した `` は、``Status: superseded [{"part":"`toolsRequiredBy`","by":["docs/adr/0092-remove-tools-required-exports.md"],"note":"で消した"}]`` になる。

### 実装の順

この ADR は、[ADR 0025](0025-extend-canonical-status-amendments.md) の `note` と URL の修正先を使う。
[ADR 0025](0025-extend-canonical-status-amendments.md) の実装をマージした後に実装する。

### 文書

`docs/specifications.md` の旧形式の参照の解決の説明を直す。
旧形式の値の読み方は変えないので、README の旧形式の値の一覧は変えない。

## 実装しないこと

- 旧形式の修正先を読めない行からの書きかえを、検査せずに通すこと。
- 行の中にない修正先を、ADRの本文から探すこと。
- `採択` と `→` のあいだの注記（golem `docs/golem-layout/adr/0034` の `採択（…）→…`）を移行スクリプトで移すこと。[ADR 0025](0025-extend-canonical-status-amendments.md) のとおり、人か AI が書く。
- 区切りとして、ここに挙げた4つのほかの語（`や`、`または` など）を読むこと。
- `Accepted → 0031` のように、英語の `Accepted` に `→` が続く行を Superseded と読むこと。この形の行は、いまの規則で Accepted と読まれ、手で新形式に書きかえるコミットが検査を通る。読み方を変えると、この形の行の状態が変わる。

## 不変条件

1. いまの規則で解決できる旧形式の行のうち、参照のあいだに区切りだけをはさむ箇所を持たない行は、この ADR の後も同じ変更の列に解決される。
2. リンクの参照の修正先は、リンク先を文書のディレクトリから解決したパスに等しい。
3. 区切りだけをはさんで続く参照は、同じ変更の修正先に、行の中の順で並ぶ。
4. 旧形式の行から得た変更は、どれも修正先を1件以上持つ。
5. 最後の参照の後ろが `は` で終わる行は、解決できない。
6. 移行スクリプトの出力の `note` は、最後の参照の後ろの文字列から、前後の空白、読点、括弧を除いたものに等しい。

| 旧形式の行（`ステータス: ` の後ろ） | 期待 |
|---|---|
| `採択→a は [ADR 0002](0002-b.md)` | 部分名 a、修正先 `docs/adr/0002-b.md`（いまと同じ） |
| `採択→a は [docs/adr/0002](0002-b.md)` | 部分名 a、修正先 `docs/adr/0002-b.md` |
| `採択→a は [0002](0002-b.md)、[0003](0003-c.md)` | 部分名 a、修正先2件 |
| `採択→a は [docs/adr/0003](0002-b.md)` | エラー（番号が違う） |
| `採択→a は [ADR 0002](0002-b.md) と [docs/adr/0003](0003-c.md)` | 部分名 a、修正先2件 |
| `採択→a は [ADR 0002](0002-b.md) で消した` | 部分名 a、修正先1件、注記「で消した」 |
| `採択→a は [ADR 0002](0002-b.md)（新しい規則）` | 部分名 a、修正先1件、注記「新しい規則」 |
| `採択→a は [ADR 0002](0002-b.md)、b は` | エラー（修正先の抜け） |
| `採択→a は ADR 0002、ADR 0003` | 部分名 a、修正先2件（いまは変更2件） |
| `採択→a は ADR 0002 と ADR 0003` | 部分名 a、修正先2件（いまは変更2件） |
| `採択→a は ADR 0002 や ADR 0003` | 変更2件（2件めの部分名は「や」） |

## テスト設計

テストの名前には、`legacy_inv` に続けて不変条件の番号を入れる。

- `legacy_inv1_unchanged`：`src/revisions.rs` と `tests/trace.rs` の既存の旧形式の入力のうち、区切りだけをはさむ参照を持たないものが、同じ変更の列に解決されることを確かめる。区切りだけをはさむ参照を持つ既存のテストがあれば、期待を新しい変更の列に直し、その旨をテストの注釈に書く。それ以外の既存のテストは変えずに通す。
- `legacy_inv2_link_destinations`：上の表のリンクの参照の行を解決し、修正先がリンク先のパスに等しいことを確かめる。モジュールのADRのディレクトリからの `../../adr/…` のリンクも含める。
- `legacy_inv3_separators`：`、`、`,`、`と`、`および` の各区切りで、修正先が同じ変更に並ぶことと、区切りでない語（`や`）では二つの変更になることを確かめる。3つの形の参照（`ADR NNNN`、リンクの参照、裸の番号）の組み合わせを含める。
- `legacy_inv4_every_change_has_targets` と `legacy_inv5_missing_target`：上の表の注記の行とエラーの行を解決する。
- `legacy_inv6_migrate_note`：移行スクリプトで、注記の行が `note` 付きの新形式に移り、二度目の `--dry-run` が差分を出さないことを確かめる。
- `legacy_inv4_pre_commit`：一時リポジトリで上の表の解決できる旧形式の行をコミットし、手で書いた新形式の行（注記を付けたものと付けないもの）へのコミットが通ることを確かめる。

### 実機での確認

実装の後、tett23 のリポジトリ（dotfiles を含む）で `--dry-run` を実行し、上の40件のうち dotfiles の `Accepted → 0031` の3件を除く37件と、send-to-kindle の4件が、移行できないADRとして報告されないことを確かめる。

## トレードオフ

- リンクの参照を修正先として読むので、リンクの文字が番号を含まない旧形式の行でも、リンク先を信じて修正先を決める。リンクの文字に番号があればリンク先と照らすが、番号が無ければ照らせない。リンク先が実在のADRであることは確かめる。
- 区切りの規則を、3つの形のどの参照にも当てる。新しく読むリンクの参照だけに当てれば、いまの規則で解決できる行の結果は変わらないが、`ADR 0002、ADR 0003` のような行は、部分名のない変更を残し続ける。部分名のない変更を減らすことを優先し、旧形式の行の読み方が変わることを受け入れる。
- 区切りに `と` と `および` を加える。部分名の中の `と`（`整数と浮動小数点数の比較`）は、参照のあいだにないので影響しない。参照のあいだの `と` が、二つの別の変更を分ける意味で書かれていると、二つの変更が一つにまとまる。調べた行に、そうした例はなかった。
- 最後の参照の後ろの注記は、比較に使わない。注記の書きかえで遷移の検査が変わらないようにし、検査を旧形式の修正先と新形式の修正先の比較に保つ。
